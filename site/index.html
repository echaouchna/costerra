§ 00 Cost estimates for Google Cloud · Terraform & Terragrunt

Know what your Google Cloud costs before you apply.

costerra reads your Terraform and Terragrunt code, prices every resource against the official Cloud Billing catalog in milliseconds, and marks up the bill with ways to spend less. You don't need terraform init or access to your projects.

§ 02 — Method

From .tf to a priced, annotated report, in one command.

Four stations, no network round trips on the critical path. Prices that need refreshing are fetched in parallel while the code is evaluated.

STATION 01

Read

Terraform root modules, Terragrunt units, mixed repositories or a plan.json. costerra discovers the projects for you.

.tf.hcl.tfvarsplan.json
STATION 02

Evaluate

Variables, locals, count and for_each, local and remote modules, and dependency outputs are all evaluated statically and in parallel.

~90 functionsmodulesmock_outputs
STATION 03

Price

Each resource is matched to its SKUs, with your contract prices when they are available. The catalog is split per service and decoded lazily.

85k SKUsSUDSpotfree tiers
STATION 04

Advise

More than 120 rules, sharpened by 30 days of Cloud Monitoring metrics when you can read them, plus Google Cloud Recommender insights. Each comes with an estimated monthly saving, its source and the data it is based on.

§ 03 — Recommendations

Every bill comes back marked up in red ink.

Add --recommendations and each finding is matched to the Terraform resource it concerns, with an estimated monthly saving. Rules that only make sense outside production, such as Spot, single-zone or no HA, are applied only there. With access to the metrics, --rightsize explains which resources are oversized or saturated (VMs, Cloud SQL, Cloud Run, BigQuery storage model), points at the line that sets the value, shows the cost after the change and links to the console to check the metrics.

§ 04 — Rightsizing

Sized from what it really uses, down or up.

With --rightsize, costerra reads the last 30 days of Cloud Monitoring metrics and BigQuery storage, and tells you which resources are oversized or saturated, why, which line of your code sets the value, and what it would cost after the change. It never edits the code: every suggestion links to the console so you can check the graphs first.

  1. i.
    WhatCompute Engine machine types, Cloud SQL tiers, Cloud Run and Cloud Functions CPU, memory and warm instances, BigQuery physical vs logical storage. Smaller when little used, larger when saturated.
  2. ii.
    WhyThe observed CPU, memory or traffic, and the threshold they crossed.
  3. iii.
    WhereThe line that sets the value: the resource block, a .tfvars file, the entry of your environment in a map, a module call, Terragrunt inputs. Project ids are read from your remote states.
  4. iv.
    CheckA link to the resource in the Google Cloud console, and the monthly cost before and after the change.

§ 05 — Continuous integration

A cost review on every pull request, with a budget that can say no.

costerra comments on each pull request with the cost diff, then updates that same comment on every push. Policies set the exit code, so a budget can block a merge. diff --base reads the base ref with git archive and never writes to the repository.

.github/workflows/costerra.yml
# abridged: copy the full file from ci/github-actions.yml
name: costerra
on:
  pull_request:
    paths: ["**/*.tf", "**/*.tfvars", "**/*.hcl", "**/costerra*.yml"]
permissions:
  contents: read
  pull-requests: write
jobs:
  cost:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with: { fetch-depth: 0 }
      - name: Estimate
        run: |
          costerra pricing sync --if-older-than 7d
          costerra diff . --base "origin/${BASE_REF}" --format markdown --out costerra.md
      - name: Comment   # creates or updates one PR comment
        run: gh api … -F body=@costerra.md
